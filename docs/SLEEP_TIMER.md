# Sleep timer

The player offers 15, 30, 45 and 60 minutes plus cancellation. A visible countdown reports the active timer. Choosing a new duration replaces its deadline. The timer counts down from selection even if playback is paused or buffering; it does not extend when songs change. Expiration pauses playback and preserves the queue, position, shuffle and repeat settings. Playing again is an explicit user action.

`SleepTimerController` is an injected singleton shared by the ViewModel and playback service. It stores an in-memory `elapsedRealtime` deadline and exposes remaining time through a StateFlow. The service owns a one-second coroutine, so navigation, activity recreation and leaving the app do not own the timer. The player uses Media3's local wake mode with the app's existing wake-lock permission so active background playback keeps the service able to observe expiration while the screen is off. There is no new alarm permission, external command, background job or server.

Service destruction cancels the timer. Process death stops the service/player and loses the in-memory deadline; recreating the service never restores autoplay or rearms an old timer. If a tick is delayed, the next tick compares against the original deadline and expires immediately. No wall-clock/date/time-zone changes can extend the timer. Finish-current-song and scheduled playback are outside this feature.

`SleepTimerControllerTest` covers delayed expiration, one-shot expiration, replacing/cancelling, and invalid choices preserving the existing timer. `SleepTimerUiTest` checks the visible choices, start/countdown/replacement/cancellation and the accessible remaining-time description. `SleepTimerServiceTest` arms a short in-process duration through the controller's bounded duration API without adding a product setting or exported test command, observes actual local audio pause with the emulator screen off and queue preservation after the activity closes, wakes the emulator, then proves cancelled timers leave playback running. The orchestrator executed these JVM, UI and screen-off service checks successfully. The service test captures the actual shuffled current occurrence and proves it stays unchanged.
