# Integration status

Initial implementation, 2026-10-25. Final verification results will be recorded after integrated checks.

## Playlist files and Echo discovery — 0.1.3 / code4

Implemented local Spotify account-data playlist JSON and Exportify CSV imports, preserving order and duplicates with all-or-nothing transactions and new playlist IDs on each import. Imported entries can be explicitly replaced per occurrence with a chosen YouTube recording; stale-position checks protect intervening edits. Home Discover uses up to three library/liked/recent artists for basic search-based discoveries, supports saving a mix, and includes a current-month New music search. Playlist smart shuffle interleaves discoveries in the session queue without changing the saved playlist. Premium-dependent Spotify login is removed from normal Settings; prior credentials remain disconnectable. Details and limits are in [INTEGRATIONS.md](INTEGRATIONS.md#spotify-playlist-files-and-echo-discovery).

Verified in this change: debug APK and both test APKs build; all 39 app/data JVM tests pass; lint has zero errors (seven warnings and three hints). Dedicated API36 emulator: three import/parser/transaction/recording-selection tests pass, two navigation/import UI tests pass, and one opt-in live test passes new-music search, saving discovery and smart-shuffle queue creation. The first UI run was interrupted by a mistakenly overlapping instrumentation run; its serial rerun passed. Initial build attempts hit stale Kotlin incremental output and Windows Gradle lint-cache locks; the successful full rebuild and final build are recorded in `build/discovery-validation.log` and `build/discovery-final-build.log`. Runtime logs: `build/playlist-import-emulator.log`, `build/discovery-ui-emulator.log`, `build/discovery-live-emulator.log`.

The import tests use synthetic exports; the user's real Spotify export and Exportify login have not been tested. Live discovery verifies results/queue construction, not recommendation quality, release dates or playback of every returned song. New-music results can include old recordings. No automatic Spotify synchronization, background release notifications or GitHub APK release publication is claimed. Existing YouTube provider/playback changes, licenses, retry limits and library data were preserved. A local source snapshot was saved under `build/preservation/` before final validation.

## Key-free YouTube playback — 2026-10-25

Implemented NewPipeExtractor v0.26.5 YouTube Music song search, stable video identities in existing library/backup storage, and lazy stream resolution inside the existing Media3 service. YouTube search is the default Discover/Search view. Results use native playback, queue, likes and playlists. Removed the Data API key UI and external-only discovery client; old encrypted credentials remain untouched and unused. No database migration or local-library reset. Provider version, required Android desugaring/shrinker rules, bundled GPL license/notices and the update procedure are recorded in [INTEGRATIONS.md](INTEGRATIONS.md#key-free-youtube-playback).

Verified in this task: debug APK and test APK build, all 46 current JVM unit tests with zero failures/errors, and lint (zero errors, seven warnings, three hints). This includes provider/downloader URL and response validation, source migration, signed URL expiry, bounded retries, playlist selection and stale search regressions. The live API36 emulator run passed both key-free song search and actual YouTube audio playback: advancing position, seeking, next duplicate queue occurrence, and fresh prepared-source resolution. An expanded live playback rerun also passed pause/resume and a recreated service restoring the saved YouTube track/position through fresh resolution. Release shrinking and unsigned release APK build passed after applying upstream NewPipe rules for Rhino's unused desktop APIs, timeago patterns and protobuf fields. Live runtime checks used the debug build; the unsigned minified release was not installed.

Normal emulator regressions passed navigation, persisted Home history, real local WAV controls/controller reconnect, notification/screen-off playback, and MediaBrowser browsing. The service-recreation check failed in the combined UI/service suite because a prior UI controller kept the service alive; the isolated rerun passed. A first expanded online attempt received CDN HTTP403 and the test aborted before the service's allowed URL refresh; its assertion was corrected to observe terminal session errors, and the final expanded run passed. This does not guarantee that every future HTTP403 can recover. No phone was accessed during this task. Live success covers the tested public Blender Foundation upload and one music search, not every recording, region, future extractor change, physical device or car host. Logs: `build/online-validation.log`, `build/online-emulator-regressions.log`, `build/online-emulator-recreation.log`, `build/online-youtube-live.log`, `build/online-youtube-restoration.log`, `build/online-release-validation.log`.
