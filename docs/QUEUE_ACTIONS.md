# Queue actions

Search result taps in all three source tabs play only the selected recording immediately. They replace the current queue occurrence at position zero while retaining the existing upcoming occurrences, repeat mode and actual shuffled traversal. With an empty queue, the selected recording starts a one-song queue. Searching never submits the whole result list as a new queue. The old current occurrence is replaced; duplicate copies elsewhere remain.

Playlist **Add playlist to queue** opens a dialog offering Playlist order, Shuffle and Smart shuffle. The dialog is outside the scrollable playlist so every choice remains visible independently of the button's scroll position. These append a block after the existing upcoming traversal and retain the current song, position and playing/paused state. Playlist order retains duplicate occurrences. Shuffle randomizes only the appended block; Smart shuffle reuses recording-based related recommendations and inserts at most one after three playlist songs. It has no artist-search recommendation fallback. Failed lookups/resolution leave the queue intact. Unsupported imported recordings are omitted just as in normal playlist playback; Offline mode admits only local/downloaded recordings, and Smart shuffle needs a connection.

Starting a new Shuffle session chooses a random playable occurrence, then creates a shuffle traversal beginning with that occurrence so repeat-off sessions can reach every song. Smart shuffle chooses a random recording anchor for a new session; an existing current playlist song retains its position when applicable. Duplicates remain independent occurrences.

The app sends bounded lists of stable library track IDs to service-owned queue commands. Only the same package and UID receive these custom commands. The service validates IDs against the durable library and resolves sources before mutation; the search replacement also checks the original occurrence/timeline after asynchronous lookup. The ExoPlayer shuffle permutation is explicitly retained across replacements and extended across append operations. Repeat-all appends rotate the existing traversal ahead of the added block, using timeline moves for non-shuffled playback so the current source is retained. At most 5000 songs/100000 ID characters per request and 10000 total queued songs are admitted.

Checks added: seeded random occurrence/anchor selection, pure append traversal order, and an emulator regression using generated local WAV tracks. The emulator scenario checks a fresh shuffled repeat-off session retains all duplicate occurrences, taps a real Library search result in normal/shuffled sessions, validates the actual next song, and appends normal/shuffled duplicate blocks without changing the current song or prior upcoming order. It does not require a live provider or modify phone data. Smart recommendation lookup retains existing live-provider test coverage; this deterministic regression does not assert recommendation quality.

The orchestrator executed the seeded/permutation JVM checks and the actual search/playlist queue emulator scenario successfully. The UI test waits for prior transient completion feedback so its physical tap reaches the queue button, and snapshots controller state together on the main thread. See INTEGRATION_STATUS.md for logs and limits.

## Arrange upcoming songs

Long-press an upcoming row's drag handle and drop on another row to change the actual next-song order. The destination highlights during dragging; edge dragging scrolls the list. Accessibility actions offer Move up and Move down. The current song is fixed. The UI captures occurrence UIDs and rejects stale drags; the service rechecks the full ordered media IDs/current index synchronously. Shuffled queues get an explicit updated shuffle permutation; normal repeat-all queues rotate around the current song before physical moves so wrapped upcoming songs remain in the requested order. No playback restart or library/playlist mutation is required.
