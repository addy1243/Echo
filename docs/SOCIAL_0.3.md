# Echo 0.3 — Phase 0 social design

> **Current candidate status, 2026-11-14:** This branch contains a Phase 1 Worker/D1 and Android/Windows candidate. It is not deployed, released, or end-to-end accepted. The production API and invite hosts are empty, so the clients fail closed. Full Echo account/cloud deletion is not implemented. Later 2026-11-13 entries below are historical feasibility records, not current implementation status.

## Phase 1 candidate — 2026-11-14

- `social/` contains the Worker, D1 migrations, API contract and tests. It requires a Google-backed Firebase ID token, verified email, signature and account-state checks. It uses an approximate Cloudflare per-IP 60/minute limiter and a strict D1 per-UID 300/day authentication quota plus action quotas. IPs are not stored in app tables or logged; Cloudflare's limiter is per location and approximate, and shared NAT users can affect each other. Each authenticated request can remove at most one quota record older than seven days; idle periods or backlogs may delay removal. The auth and cleanup writes consume D1 free quota. All services share their account's free quotas. No paid plan or billing may be enabled.
- Unique case-insensitive usernames, built-in avatars, profile settings, request/accept/decline/cancel, friend removal, blocking/unblocking and 24-hour one-use invite candidates exist. Invite creation is unavailable until an owner-approved HTTPS invite landing/deep-link host is configured; app invite origins are blank. No online status, current-song activity or listening session is published in Phase 1.
- Relationship actions carry opaque actor/target lifecycle nonces, atomically rotated with mutations. Read-only lookups do not allocate pair rows; concurrent actions may conflict across different relationships and clients must refresh on 409. Social deletion advances the setup epoch and rotates the nonce, removes the profile and owned edges, preserves blocks created by others, and retains an opaque lifecycle record for stale-action safety. D1 Free recovery can retain deleted data for up to seven days. Full account/library/RTDB/Auth deletion remains unimplemented; current client rules deny private-library delete.
- **Executed evidence:** Worker unit tests and isolated local D1 integration use synthetic Google-linked identities and a mocked IP binding, not live Google sign-in. Android and desktop focused JVM tests exercise the disabled-by-default clients. An earlier isolated Cloudflare remote preview verified a real synthetic Firebase token before Google-provider/IP-binding changes; it is not a test of the final Worker or a production IAM grant. Isolated Firebase social identity was denied synthetic private-library reads/writes; a separate test deletion role could delete synthetic data but had database-wide delete authority. Exact current test results and remaining reviews are in [LOGS.md](LOGS.md).
- **Independent review:** A fresh high-reasoning review of the final nonce, invitation, block and quota paths found no actionable security issues. Its Worker unit run passed 8/8; its separate integration rerun was blocked by sandbox loopback access, while the orchestrator local integration run passed.
- **Remaining gates:** verify real Google identity and deployed Cloudflare rate-limit binding in an isolated project; implement and test the separately scoped full-deletion lifecycle; provision/verify an invite host and Android/Windows link handling under separate authorization; run native/emulator accessibility and cross-platform acceptance. Do not deploy, publish, enable billing, or alter production rules without owner authorization.

## Cloudflare free-plan feasibility — 2026-11-13

The owner selected the Cloudflare route for investigation under the zero-cost constraint. Workers Free and D1 are a plausible trusted API and social database; they are not provisioned or verified. Correction: the account's 5 GB free total is capped at **500 MB per database**, with at most 10 free databases. Other published limits include 100,000 Worker requests/day, 10 ms CPU/invocation, and 5 million D1 rows read and 100,000 rows written/day. D1 queries fail after daily limits and reset at midnight UTC. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/), [D1 quota enforcement](https://developers.cloudflare.com/changelog/product/d1/).

D1 `batch()` executes a transaction and rolls back on error; use unique constraints and conditional mutations to serialize username claims, invite redemption, relationship and block changes. A single D1 database queues queries and can overload; test actual contention. Cloudflare's built-in rate limiter is approximate and per-location; strict account limits need a tested authoritative transactional counter or Durable Object, with no claims of global IP/device accuracy. [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/), [rate limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

An API can verify Firebase token signature and project claims with public keys without private-library credentials. Signature verification alone does not establish revocation: Firebase documents an Auth backend check. End-user `accounts:lookup` plus `validSince` is a possible credential-minimizing approach, but must be compared to Firebase's documented revocation-aware Admin behavior in an isolated project, including disabled/deleted accounts, token revocation, and outages. Do not log token or account response. Test the deployed identity and all effective permissions; no social identity may read the private library. [Verify ID tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens), [revocation](https://firebase.google.com/docs/auth/admin/manage-sessions), [account lookup](https://docs.cloud.google.com/identity-platform/docs/use-rest-api).

Full deletion still needs a separately tested privileged lifecycle and a way to finish after interruption, covering private Firestore, RTDB, Firebase Auth and social records. Social deletion must account for Cloudflare free Time Travel retaining recovery history for seven days. No claim of immediate irreversible purge. [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/). A local Python/SQLite experiment with eight concurrent contenders produced one username claim and one invite redemption, and rejected an expired invite. This is not a D1, Worker or end-to-end authorization test. Wrangler 4.161.0 was installed in a temporary directory and Cloudflare sign-in succeeded with account, Worker and D1 scopes; D1 list showed no databases. A local D1 harness started, but its assertions did not run because of harness configuration errors. No D1 race or rollback result was obtained. ## Phase 0 feasibility findings — 2026-11-13

- **Gate remains open.** A trusted HTTPS API can verify Firebase ID tokens from Android and Windows, but neither hosting nor identity isolation has been exercised in an isolated project. The current project, its IAM grants and billing state were not inspected. No assumption about deployed permissions is evidence.
- **Isolation:** Firestore server client libraries bypass Security Rules. The existing default database contains private `users/{uid}/sync/library-v1`; its client rules allow verified owners to get and write but deny client deletion. A social service with database-wide entity access could access it. Separate named database IAM conditions are a candidate boundary, subject to testing effective inherited grants and exact identity access; a separate project is a stronger administrative boundary, but requires explicit verification of tokens issued by the existing auth project and coordinated deletion. Neither design has been proven here. A separately scoped deletion worker needs its own tested permissions and fail-closed resumable workflow.
- **Cost:** Firebase Functions deployment requires Blaze; a normal Cloud Run project requires linked billing, even if usage falls within no-cost allowances. Firestore has one free database per project; an additional named database requires billing and is charged for usage. A separate project may have its own free database quota, but hosting and operations still require evaluation. Free quota is 50,000 reads and 20,000 writes/deletes per day and 1 GiB storage; TTL deletes require billing. The later-phase illustrative 120,000 reads/day already exceeds the free read quota before authorization and retries. Alerts are not spending caps. No billing was enabled.
- **Alternatives:** Direct client Firestore plus Security Rules can operate within Spark quotas, but needs a new proven transaction/rules and abuse-control design; it does not automatically meet this plan's server-only lookup, throttling and revocation requirements. RTDB would add a cross-service authorization boundary. An external free host might avoid Google hosting billing but introduces its own quotas, credential management, abuse controls, uptime and deletion operations; no provider has been selected or verified. App Check is not authorization, and Windows would need a validated custom provider.
- **Next gate:** select an isolation/hosting arrangement with the owner, then use a synthetic test project to verify the social identity can operate only on its social database and is denied private-library read/write; test the deletion worker separately, token audience and revocation, concurrency, quotas and platform clients. An emulator alone cannot prove cloud IAM. Full account deletion also needs a reviewed privilege and retry plan covering library, RTDB, social state and Auth without erasing the local library.

This is intended for a few friends, with no public rooms, and should cost as little as practical. Social targets 0.3; separate 0.2.7 work must not be disturbed.

## Product and privacy

Social setup is optional after sign-in and independent of library sync. Recommend a display name, case-insensitive unique ASCII username (3–24 letters, digits, underscore; store canonical lowercase), and built-in avatar. Reserve sensitive names and validate on the server. Explain that exact username lookup exposes the minimal profile to signed-in users; no email search, contact upload, bio, custom image or directory browsing. Name changes use an atomic new claim/release, a cooldown and a short old-name quarantine; exact duration is an owner choice. Avoid promising that a username proves real-world identity.

An invite is a cryptographically random, single-use bearer secret delivered in a link, with the owner-approved 24-hour lifetime. Recommend 128+ random bits, owner revocation and server-stored hash only. Preview shows minimal profile and requires explicit friend request and subsequent acceptance; possession never auto-friends or joins a session. App universal/deep link handling validates host, path and token; an HTTPS landing page must avoid analytics, referrer leakage, logs and third-party assets containing the token. Rotate/revoke and show expiry; never send secrets to crash logs. Exact username and valid invite lead to the same consented request flow.

State transitions: none → pending → accepted, or pending → declined/cancelled/expired; accepted → removed. Requests are bounded, idempotent and reject self, blocks and stale versions; reciprocal simultaneous requests may atomically become accepted only if both requests are explicit. A block silently cancels requests/invites between the pair, ends friendship and revokes activity/session access in both directions; avoid revealing who blocked whom. Unblock never restores friendship. Both can remove a friend. Retry returns the authoritative state, not duplicate requests.

The owner chose independent **online visibility** and **current-song visibility** switches that both start on in social setup, for friends only. Show what each shares before the user confirms setup; allow either switch to be turned off during setup or later. A persistent private-listening control disables current-song publication across the account, without implicitly changing online visibility. Sign-in alone does not publish activity before social setup is confirmed. Do not publish private/local filenames, queue, device names, history, library, paths, audio, signed URLs or credentials. Only bounded portable exact recording identity, title/artist and playing/paused status are eligible. An unavailable recording is reported; manual search may be offered but never substituted automatically. Data already viewed, cached, screenshotted or copied cannot be recalled.

**Deletion recommendation:** separate social-profile deletion from full Echo account/cloud deletion and local sign-out. Require explicit confirmation and recent reauthentication for full deletion, explain local library retention and cloud consequences. Immediately mark the account deleting in the authoritative store and deny social reads/actions, revoke sessions/invites and stop writes; an idempotent server job removes handles, edges, requests, projections, sessions, activity and the explicitly selected cloud library, then deletes Firebase Auth last, with retries and visible pending/failure status. This requires new privileged deletion authority: existing Firestore library rules deny client deletion. Audit all legacy account data and backups, set concrete retention/deletion deadlines before launch, and test direct Auth deletion and interrupted jobs; do not claim deleted data is immediately removed from backups or other users' devices. Handle reuse only after quarantine. Sign-out alone preserves local library and is not deletion.

Create the deletion job and increment a durable deleting generation in one transaction; all social creation and mutation transactions read the lifecycle so concurrent writes conflict and retry. Use server-maintained, queryable participant indexes to enumerate pairs, invites, memberships and hosted sessions by either endpoint; cleanup is idempotent and cursor-based, and the deny tombstone remains until retries and all fan-out finish. Test direct Firebase Auth self-deletion and determine how to prevent or reliably recover cleanup if it bypasses this workflow before launch; do not assume a trigger always runs or an already-deleted user can restart the job.

## Presence and activity

Recommend a server-stamped lease per authenticated installation session: fresh for 90 seconds, heartbeat at most every 30 seconds while participating, with 15-second polling for viewed friend lists only as initial sizing assumptions to test. Presence means Echo recently checked in, not that the person is available. A per-device random session ID changes on restart; late writes from a superseded session are rejected. Client reports sanitized playback only when both account consent and per-device participation are active; current-song off or private mode sends a server revocation that prevents further reads and clears activity. A trusted server assigns timestamps and arbitrates deterministically: freshest eligible playing device, then freshest paused device, tie-break by opaque session ID; never expose device identity. A local/ineligible recording hides the track, not its filename. Consent is account-wide: stale devices cannot re-enable it.

On privacy-off, hide locally immediately and submit the change; confirm remote revocation only after the server commits. Offline, show “change pending”; until accepted, previously published activity may be visible until its lease expires. At read time the service checks server time and current consent and never returns expired activity, even if cleanup is delayed. After 90 seconds without a heartbeat show offline/unknown, not a false precise last-seen; on reconnect obtain fresh consent and new session before publishing. Abrupt crashes, suspend, clock skew and partial network are normal. No `onDisconnect` guarantee is assumed for Echo's REST transport; a later SDK-based option needs independent cross-platform verification. Cleanup/TTL is storage hygiene, not the access-control clock. Scope session membership and presence separately.

An already authorized response can arrive after a revocation acknowledgement; honest clients discard responses superseded by a known consent or membership generation, but a malicious recipient cannot be made to forget data. Strict prevention of any arrival after acknowledgement requires a separately designed drain/ack protocol and still cannot recall data already delivered.

## Private listening and queue

Recommend one participant per account per session, one active social session per participating device, at most eight participants including host initially; validate capacity and costs before confirming limits. Host invites an existing unblocked friend; invite expires (recommend 10 minutes) and identifies a specific recipient/session. Guest explicitly joins after seeing host, current track and the fact that their local queue will be temporarily set aside. No link alone grants membership. Participants play locally; no audio is relayed. A session is not a same-account remote control and does not reveal independent queues.

States: invited → joining/preparing → active → reconnecting → left/removed/ended; a fresh device session must reauthenticate and rejoin within the owner-accepted two-minute grace period. Only host changes play/pause/seek/skip, queue order/removal and ends the session. Guests leave and suggest eligible exact recordings; the host accepts/rejects by default. When direct-add is enabled, members may append only, not change transport, remove or reorder. The UI identifies author and current mode; toggling mode applies to future submissions, never silently approves existing suggestions. Cap queue and outstanding suggestions, rate-limit, and use user-visible rejection. No public room or automatic host transfer: host loss pauses the shared timeline, permits a short reconnect, then ends the session; removing or blocking a guest immediately revokes their future reads/actions and removes them from the membership view. If one guest blocks another, the blocking guest immediately leaves the session, as the owner chose.

Each item has a fresh occurrence ID distinct from its canonical recording ID, preserving duplicates and order. Idempotency keys, session ID/epoch, host device session, membership generation, queue revision, timeline sequence and expected occurrence guard mutations. Server transactions authorize role and membership at commit, serialize acceptance/direct-add and assign sequence; retries return the committed result. Seek captures the timeline and occurrence; stale actions fail visibly and refresh. Mode changes and blocks race safely with submissions by checking the same authoritative records in the transaction. Appending must not restart or replace the current item or alter play/pause/position; if safe append cannot be built, disable it until it can. Local playback resolves stable portable IDs independently; never transfer resolved URLs or silently replace an unavailable track.

Before joining, snapshot the local queue, traversal, current occurrence, position and play state in the platform's existing recovery store. Only commit shared playback after guest consent and preparation. On leave, removal, expiry, host loss or restart, restore the independent queue **paused**, preserving duplicates and traversal; if recovery fails, preserve the snapshot and explain, never overwrite the user's saved playlists. Stage a queue change before commit when all affected participants must prepare: precommit failure leaves prior timeline intact; after commit, failure is partial/unknown and each affected client reports it. A late joiner loads authoritative revision, resolves locally, catches up or reports unsupported/buffering; a disconnected guest cannot issue queued offline mutations and must reauthorize membership on reconnect. Revocation stops future server access but cannot forcibly stop an offline client or erase cached media.

The existence and durability of a suitable recovery store on both platforms are unverified. Before Phase 3, test crash/restart with duplicate occurrence IDs, shuffle traversal and position against the selected baseline, and design minimal storage changes if required. Define a versioned portable wire contract and prove both Android emulator and Windows interpret recording IDs, occurrence IDs, epochs, revisions, unsupported tracks and postcommit failures consistently before relying on shared helpers.

Timing is best effort, not sample-accurate or speaker-delay measurement. Reuse proven pure timing/queue helpers only after checking 0.2.7 interfaces; independent account/device/session identities and authorization are new. Device clock uncertainty, network loss, different recordings' availability, buffering, latency and partial postcommit outcomes must be surfaced. Host decides whether to pause or continue when a participant cannot resolve; no fake success.

## Backend, security and revocation — original Firestore proposal

The original proposal used Firestore as the **single authoritative social store** and a small authenticated trusted API for every social read and mutation; the owner now prefers evaluating Cloudflare Workers/D1 Free as described above, so the following Firestore schema is historical design context and not the chosen implementation. Under the original proposal, clients have no direct access to social paths. The existing RTDB owner-only paths and Firestore library path stay unchanged. Use bounded short polling only while social views/sessions are active; this is a cost/latency tradeoff, not a final scalability claim. Do not add RTDB listeners, fan-out replicas, FCM or a custom always-on server until measurements justify them. If moving session state to RTDB later, require a separate design proving revocation under propagation failures; Firestore rules cannot consult RTDB and RTDB rules cannot consult Firestore.

Illustrative server-only Firestore collections (paths and exact indexes are design, not deployed schema):

| Record | Minimum contents and authority |
| --- | --- |
| `socialProfiles/{uid}` | sanitized display name, canonical handle, avatar, consent flags, lifecycle/generation; subject edits via API |
| `socialHandles/{normalized}` | owner UID, reservation state/generation; server transaction uniquely claims |
| `socialPairs/{orderedPair}` | two UIDs, pending/accepted/removed and version, block flags; server only |
| `socialInvites/{hash}` | owner, expiry, use/revocation generation; no raw secret |
| `socialDevices/{uid}/leases/{sessionId}` | server time, bounded status/portable recording, expiry, generation; server only |
| `socialSessions/{id}` | host UID/device session, epoch, state, mode, timeline/revision, expiry and bounded queue |
| `socialSessions/{id}/members/{uid}` | explicit membership, role, generation, device session and lease |
| `socialSessions/{id}/suggestions/{id}` | bounded metadata, submitter, status, idempotency key and revision |
| `socialJobs/{id}` | deletion/retry progress and minimal audit metadata; restricted operator access |

No client may read lists, enumerate handles or write these records directly. API verifies Firebase ID token, verified account and subject, schema/size and current account lifecycle. Exact lookup is authenticated and throttled; relationship-dependent reads check both block flags and current accepted pair; session reads/actions also check current membership, role and session state. Public-facing profile lookup must check blocks without leaking their existence. Mutations use Firestore transactions with bounded reads and explicit idempotency; actions that race with block, unfriend, privacy-off or membership removal read/write the same authoritative authorization records so a conflicting commit is retried and rechecked. For protected reads use a consistent transaction/snapshot and check authorization before returning data. Define the linearization point as the committed read/write transaction: an in-flight response authorized before revocation can still arrive afterward. No cross-service projection is trusted for an access decision. A verified-ID token alone does not prove fresh authorization; rules for owner paths and service IAM remain separate. Server SDK bypasses Firestore rules: least-privilege service identity, restricted deployment/invocation, input validation, audit, and deny-by-default rules are mandatory. Test the precise transaction semantics and Firestore operation/rule limits before selecting batch sizes. Never put invite secrets or listening history in logs.

Before Phase 1 prove an actual IAM boundary, not merely a policy intention: use keyless workload identity, restrict invocation and deployment, inventory supported resource-level IAM and test whether the social service identity can read or mutate the private library. If the same database cannot enforce the required separation, evaluate a separately isolated database/project and its authentication, deletion, cost and operations implications; do not claim document-level isolation from IAM without evidence. Give the deletion worker separately scoped privileges and test both identities. This is a blocking feasibility decision, not an existing protection.

Abuse controls must be server-enforced and concurrency-safe: per-account and per-IP/device signals for lookup, requests, invites and joins, bounded per-user friends, queue/suggestion counts and payload sizes, cooldowns, expiry, replay protection, anomaly monitoring and escalating throttles. IP signals are not stable identity and must have documented retention. The owner intends a small private group of friends; a reporting or moderation product is not in scope. Retain blocking and basic safeguards even for private use. App Check may reduce some abuse but is not identity or a substitute for server authorization, and Windows support/attestation must be validated. Budget alerts are alerts, not spending caps. Add kill switches for new social actions and session creation, plus operational controls for existing sessions; keep independent playback working.

Threats and checks: handle squatting/enumeration → atomic claim, exact lookup and quotas; leaked invite → high entropy, expiry, one use, revocation and no auto-accept; impersonation → verified auth, explicit identity and consent; stranger/blocked ex-friend → authoritative checks on each read/action; malicious member forging host writes → server role/session/version checks; spam and oversized queues → quotas and bounded payloads; compromised/stale client or replay → epochs, idempotency, authorization at commit; listener/cached data after revocation → no direct listeners, recheck each poll, honest residual disclosure; admin misuse → least privilege and audit; abandoned account/deletion → fail-closed lifecycle and resumable cleanup; cost exhaustion → quotas, alerts and kill switch. TLS and token redaction apply everywhere. Firebase refresh-token revocation alone does not immediately invalidate an already issued ID token for all ordinary rule checks; use authoritative lifecycle checks and revocation-aware verification where appropriate.

## Delivery, compatibility and operations

Android UI/profile and service lifecycle stay in app/playback adapters; Windows UI, tray lifecycle, account protection and LibVLC remain desktop-specific. Small pure models/validators belong in shared ownership only when genuinely common; include the desktop source-set build in checks. No Google email is displayed to friends. Old clients continue owner-only library and same-account playback; social records are additive and versioned, and unsupported clients do not participate. Never rewrite existing library or queue schemas for social. Capability/version negotiation disables unsupported session operations; no automatic upgrades or version bump in Phase 0. Verify OS background execution restrictions and deep-link ownership for both platforms. Check provider terms and recording availability for the precise source and regions before deployment; this design is not legal or availability verification.

Rollback disables creation and writes first, marks active sessions ended where possible, removes social reads via the API/deny rules, and leaves existing private sync/playback and local queues intact. Keep schema readers and old rules compatible until the old clients age out; do not delete data as a rollback shortcut. Use isolated Firebase project/emulators with synthetic accounts before any owner-authorized production deployment. Establish service account access, deploy/revert runbook, incident response, logs without tokens or song history, retention, quotas, dashboards, backup and deletion policy. Firestore TTL is asynchronous and may incur charges; never use it to enforce expiry. API billing and availability, deployment tier, location, App Check and rate-limit backing store must be validated before commitment.

Illustrative load, not a price quote: 100 daily active users, 10 viewed friends, 30 minutes of an open list, polling each 15 s gives 120 polls/user/day; if each poll reads 10 friend records, 120,000 document reads/day before authorization records, retries, session reads and writes. With 30 s heartbeat for 30 minutes, 6,000 lease updates/day for 100 active devices, before activity changes. Actual batching, indexes, minimum query charges, server/API/network and concurrency change this; measure with emulator and a capped test project, then use current regional prices and a workload model. [Firestore pricing](https://firebase.google.com/docs/firestore/pricing), [RTDB billing](https://firebase.google.com/docs/database/usage/billing), and [Firebase pricing](https://firebase.google.com/pricing/) are references, not an approved estimate.

## Verification and phase gates

Phase 0 gate: owner reviews the choices below and security architecture; select the baseline and resolve the feasibility spikes before Phase 1 implementation. Phase 1 profiles/friends: transactional uniqueness and concurrent accept/block; normalized handles, reserved words, link expiry/replay/revoke, deletion, auth and quota tests. Phase 2 activity: consent defaults, multi-device selection, offline privacy toggle, lease boundaries/server clock, cached data, restart and crash, ineligible tracks and cost. Phase 3 sessions: two isolated accounts with Android emulator and Windows, explicit consent, roles, block/unfriend races, reconnect, host loss, unavailable tracks, saved queue recovery and honest timing/partial failure. Phase 4 collaboration: concurrent approvals/direct-add/mode switch, duplicates, attribution, stale actions, idempotency and no playback restart. Phase 5 integrated acceptance: accessibility, mixed clients, failure injection, load/billing and independent security review before separately authorized shipping. Public rooms and optional extras require their own approved scope.

For every phase run shared model/transaction tests, Firebase Emulator Suite security tests against deny-by-default social rules, privileged API authorization tests with multiple users and malicious inputs, and targeted Android/Windows build and UI tests. Include delayed responses, retries, simultaneous revocation/read/write, cleanup failure and token expiry. Simulations prove neither backend rules nor acoustic sync. Native acceptance uses only a dedicated Android emulator and Windows test profile, preserving existing app data and signing identities; no physical phone. Measure real-network timing separately with clear tolerances. Do not claim a check passed until executed.

## Owner decisions and remaining feasibility

The owner accepted unique usernames and exact lookup, the proposed 3–24 character format and 24-hour single-use links; separate social and full account deletion with local library retained; and the proposed initial session defaults (eight participants, one account per session, ten-minute invitations, two-minute host reconnect, no host transfer, host-only transport). Both visibility switches start on during social setup and remain independently changeable. A guest who blocks another guest leaves immediately. The intended audience is a few friends; public rooms, chat and a reporting/moderation product are out of scope.

The owner wants the service as free as possible. This is a cost objective, not authorization to enable billing or a guarantee of zero cost. Compare the recommended trusted API plus Firestore against realistic free-tier quotas and alternatives, including whether deployment requires billing, Android/Windows support, abuse protection and revocation; select only after measuring. Exact rename cooldown, username quarantine, deletion retention and hosting/billing details remain implementation decisions to resolve from feasibility and actual workload, without blocking independent baseline reconciliation.
