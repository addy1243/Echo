# Echo Music architecture

Echo is a Kotlin music player with two application shells: Android and Windows desktop. Five Gradle modules are included: core, data, playback, app, and desktop.

## Module ownership

- **core** owns small platform-independent domain models and contracts used by both applications. Keep Android framework classes, persistence details, provider clients, and UI out of core.
- **data** owns Android library persistence, Room and MediaStore adapters, settings, provider integrations, import parsing, offline repository policy, and shared account/connected-playback transport models. Provider-specific extraction stays behind provider interfaces.
- **playback** owns the Android Media3 playback service, source resolution, durable queue traversal, Android Auto browsing, and service/controller boundary. ExoPlayer is owned by EchoPlaybackService; the Activity/UI controls it through MediaController.
- **app** owns Android composition: Hilt wiring, Compose screens, navigation, view models, account/settings flows, and app-update UI. It depends on core, data, and playback.
- **desktop** owns the Compose JVM Windows shell, local desktop persistence, Windows account protection, LibVLC playback, MSI packaging, and desktop-specific adapters. Its Gradle source set reuses selected pure Kotlin provider, Firebase, matching, and app-helper source files. Android storage and UI are not reused as desktop persistence or screens.

Keep dependencies pointing toward domain contracts. Platform state crosses through explicit repositories/controllers/adapters. Put a reusable function in the module that owns the behavior; both app shells should call the existing shared implementation when they truly share that behavior. Do not duplicate workflows or move platform-specific behavior into a shared module merely to reduce line count.

## Runtime paths

**Android playback:** Compose screen and ViewModel → MediaController → Media3 service → library/source resolver → local file, cached audio, or provider stream. The service resolves stable library IDs again and does not trust a URL supplied by the UI. It owns the queue, player, audio focus, notification, repeat/shuffle traversal, queue restoration, sleep timer, and connected-playback sessions after a foreground start. Activity backgrounding must not stop its connected session; process/service termination ends participation and needs runtime acceptance.

**Windows playback:** Compose desktop UI → desktop playback/session state → LibVLC engine and desktop source resolver. Closing the main window hides it to the system tray, leaving playback and connected-device presence active until tray Quit. Windows stores its own local library/configuration and DPAPI-protected account material. The VLC 3 x64 installation is an external runtime dependency; Echo does not bundle or silently install it.

**Windows stage simulation:** `-Decho.staging=true` selects `StageConnectedPlayback` at desktop composition time through the same `DesktopConnectedPlaybackBackend` contract used by the Firebase-backed client. The in-memory simulator owns fixture sessions, remote queues, Move backups, group membership, and a shared group timeline. The stage-only Admin floating action adds/removes or toggles demo peers and selects simulated 20 ms, 500 ms, or variable network estimates; focused player actions route through the simulator. Initial group start, Sync, and shared-queue replacement use the same bounded common-deadline helper as the live protocol. Leaving restores each private queue paused. On an empty isolated library, the stage seeds three demo recordings and a `Stage Mix` playlist, so song/playlist selection exercises remote and shared-queue replacement. Staging bypasses connected Firebase participation and automatic library sync, hides account entry, and uses a separate library file. Automatic YouTube discovery is disabled; manual search remains an explicit online action. Fixture playback is silent. Presets supply synthetic timing estimates and do not add packet delay. This validates desktop UI routing and local state transitions, not RTDB transport, real device timing, or audio.

**Android stage simulation:** `stageDebug` creates `dev.echo.music.stage` with an isolated app profile and OAuth callback scheme, so it can coexist with normal Echo. The app-local `AndroidStagePlayback` owns demo peers and their silent queue snapshots; the stage-only floating Admin action adds Android/laptop peers with unique available labels, disconnects/reconnects them with new session IDs, changes simulated 20 ms, 500 ms, or variable network estimates, and removes them. Reconnection freezes progress accumulated while offline and preserves the peer's queue. Stage seeds three silent recordings and `Stage Mix` in its isolated library. Focused peer transport, monotonic simulated progress, read-only queue snapshots, selected-song/playlist queue replacement, Play together, and paused private-queue restoration stay in the simulator; queue replacements get fresh occurrence IDs/revisions and preserve duplicates. Initial group start, Sync, and shared-queue replacement use the shared bounded common deadline; the group reports Preparing until it arrives and projects a playing position to that start. Firebase participation, Google account entry/sync, automatic discovery, and updater checks are disabled. Move remains unavailable in Android Stage. Manual Search and ordinary local playback still use their normal providers. Presets are simulated estimates, not real packet delay. This validates emulator UI and local routing, not RTDB, real device transport, or acoustic synchronization.

**Account data:** Android AccountManager/Google account provider and Windows browser PKCE obtain a verified Google identity; both use the same Firebase project. Firestore sync stores bounded library metadata after consent. Realtime Database carries a separate short-lived connected-playback channel. Neither sync path transfers audio, credentials, local file paths, signed streams, or access tokens.

**Release updates:** Android checks GitHub Releases for a newer APK and verifies size, digest, package, SDK, and installed signer before private staging and a user-confirmed Android installer handoff. Windows checks releases independently for an MSI, verifies HTTPS/host, size, digest, and MSI identity, then starts the normal interactive Windows Installer. Windows program files and user library/credentials have separate directories.

## Player surfaces and target routing

Android and Windows each expose platform-local floating dock and full-player Compose functions. The dock is compact and the full player keeps larger cover art. The surfaces reuse leaf controls for status, progress, favorite/playlist actions, device selection, and queue access. Keep platform UI functions in `app` and `desktop`; there is no shared Compose UI module. Each shell derives one player presentation state from its playback service/engine and dispatches semantic intents such as play selected queue, append, play next, seek, favorite, playlist membership, and open queue.

The application shell owns focus among Local, one explicitly selected remote device, or one active Play together group. The Windows multi-player dock uses one ordered focus helper for both swipe and its overlapping right-side deck: Local followed by sorted independent live peers. The deck contains every eligible independent target, including the focused one, raises the selected card, and exposes the others as overlapping tabs that prioritize device identity. The focused card shows artwork and current song/status; other cards remain informational and selectable. Main-player transport and song/playlist actions route to the selected target. The deck hides when there is only one eligible target. The compact dock's Devices popup is removed; the full-player device picker remains available for group and direct selection controls. Group members never enter this deck. When a peer is focused, cards wrap through the remaining peers and Local. Android uses one common compact two-row card for Local, remote, and Play together inside the font-scale-aware `PlayerDeckState` carousel. Its top row has circular 40 dp artwork, device identity (or `Together · N devices`), separate single-line title and artist, and a 48 dp Play/Pause control. The bottom row has 48 dp Previous and Next controls around the shared accessible seek slider. The card is 112 dp at default font scale and about 134 dp at 1.5×; exceptional readiness status adds a scaled metadata line. It fits the 320 dp dock while retaining a visible 48 dp next-player peek. `PlayerSeekBar` is the app-local seek function shared by dock and full-player surfaces, with a 48 dp touch area, 4 dp track, and 12 dp thumb. It captures the seek target at drag start, stages movement locally, and dispatches once on release: Local validates the captured Media3 window UID, remote validates its captured device/session and playback revisions, and Play together validates group ref, timeline sequence, and occurrence. A changed target/timeline rejects the stale seek, and pager swipes are disabled while scrubbing. Other cards are selection-only. One target has no next-player peek; multiple targets retain the same card geometry. Swiping pages through stable keys and tapping the visible next-card edge advances focus. Each remote key includes its exact device id and session id; list changes reconcile against the selected key before a settled page can change ViewModel focus. There is no compact device picker. The base/null entry is Local when no group is active and Play together when one is active; group members are excluded from the independent device entries. Stale selected remotes remain visible as reconnecting until the user selects a fresh session. The full player reads the same focused presentation and names the active output. An active group keeps the dock visible even with no local song; newly online peers update the deck without stealing focus. If a focused peer disconnects or starts a new session, keep its page visible as reconnecting and disable commands until the user selects a fresh session. One device may join only one active group. Play together selects two to eight same-account devices total, including the coordinator; other peers remain independently available. When active, Play together occupies the base/null carousel position, with the same common card layout; individual group members remain outside the independent device entries. Group members are listed with readiness/status in its Devices panel. Leaving returns focus to the coordinator's local player with its independent queue paused.

The Windows dock and each deck card reuse `desktopPlayerPresentation` for Local or a remote `ConnectedDevice`; swipe and deck order share the independent-player ordering helper. The focused player shows the selected device name. Cards capture the exact device/session and only select focus; they do not carry favorite, playlist, or download actions. Focused-player/full-player library actions retain their existing track and revision guards. Downloads require a canonical YouTube recording and are disabled in stage mode, where demo IDs must never reach the real downloader.

Playback intents route through one shell-level dispatcher. Local intents use the Android MediaController/service or desktop playback engine. A single remote target uses a connected-playback queue operation; the receiver validates account, device/session identity, and captured queue revision, resolves stable portable recording identities locally, then acknowledges the change. Queue payloads are bounded and contain only portable recording metadata plus unique queue occurrence IDs; local file paths and resolved stream URLs never cross devices. Clicking a song/playlist replaces the focused remote/group queue from that occurrence. Append and Play next on remote/group queues remain disabled because the current replacement operation would restart playback; remote queue viewing is a read-only snapshot. Windows full-player device/group selection and platform-specific transport controls remain behind their existing adapters.

Play together uses the common Android compact card layout and does not have a group-specific tinted geometry. Its top row has `Together · N devices`, title, and artist beside circular 40 dp artwork, with Play/Pause; its second row holds Previous, the shared seek, and Next. The baseline is 112 dp (about 134 dp at 1.5×); exceptional readiness status adds a scaled line. The card fits the 320 dp dock and retains the 48 dp next-player peek. All transport and seek targets remain 48 dp across Local, remote, and group focus. The details panel lists the coordinator, each member's readiness, and a fresh RTT/jitter network estimate matched to that member's current session. Missing estimates show the bounded fallback; the copy states that speaker/output delay is not measured. `Sync now` becomes `Adjusting timing…` while the common deadline is pending.

Play together queue replacement is a V2 group operation guarded by group epoch, exact member sessions, and timeline sequence. Replacing the queue begins at the selected occurrence and preserves the playlist remainder, order, and duplicates. Every active member must be present and capable; each resolves and stages the new queue before the coordinator commits it. A precommit failure aborts staging and keeps the previous shared queue. After commit, incomplete activation is reported as partial/unknown and must not claim the old queue was retained. The initial READY activation, Sync, and shared-queue commit use one server-time deadline. For each current member, timing telemetry retains a bounded rolling set of control-request RTT and clock samples. The coordinator selects a lead from the slowest fresh session: eight serial RTT rounds plus jitter, server-clock uncertainty, one poll interval, and a safety margin, with a 1.5-second minimum and 8-second maximum. If any sample is missing, stale, or the zero-RTT warm-up placeholder, all members use a non-adaptive 8-second start. The playing coordinator position is projected to T before commit; paused position is unchanged. Every client waits on a monotonic local deadline and checks group ref/epoch, exact session, timeline sequence, and occurrence before applying. A late client catches up to the current timeline; group drift checks use a tighter 120 ms threshold. This compensates for control-path readiness without treating internet RTT as speaker latency or promising sample-accurate acoustic synchronization. Timing telemetry is a separate, owner-authenticated additive RTDB child; the corresponding rules are not deployed by this work. Queue and Sync capabilities are advertised so mixed-version groups can disable unsupported actions.

Shared seeking stages slider movement in the UI and submits once on release. The request carries the captured group ref, timeline sequence, and queue occurrence ID; `ConnectedPlaybackV2` checks all three against the current timeline before creating the group action. If the track or timeline changes during a drag, the stale seek is rejected. Remote seeking likewise dispatches to the captured device session after the gesture.

## Shared data contracts

- The canonical recording model is Track. Stable provider-scoped identities and canonical public watch links may be saved; short-lived audio URLs are resolved at playback and are never persisted.
- A track ID describes a recording; each playlist or queue occurrence has its own position/identity. Duplicate occurrences are expected.
- Firebase library sync and connected playback are separate protocols and rules. Keep Firestore playlist/favorite/history contracts intact when changing the RTDB playback protocol.
- Platform adapters capture an expected snapshot/revision before asynchronous work and validate it again before mutation. Apply multi-row sync/playlist replacement atomically and preserve local file associations.
- Local library and playback should remain usable without account sync, network access, or a connected peer.

## Change placement guide

- Add pure model behavior or a shared parser to core/data only when it has no Android or desktop framework dependency.
- Add an Android persistence/provider/service change to data or playback; connect it through app composition rather than reaching into a screen from the service.
- Add Windows persistence, native-player, installer, or window behavior in desktop.
- If both frontends need behavior, identify the owner module and expose a small stable contract/function. Keep platform permission, credential protection, and lifecycle handling in the platform adapter.
- Before changing a schema, queue protocol, account payload, updater contract, signing identity, or installer identity, read the corresponding requirements in [docs/IMP.md](IMP.md) and use the focused acceptance checks documented there.

## Build topology

The Gradle root includes all five modules. The desktop app includes selected files from data and app source roots; changing Kotlin visibility, imports, package ownership, or Android-only dependencies can therefore break desktop even when Android compiles. Run relevant checks in both source sets when editing shared files.

Android targets API 36, minimum API 26, and Java/Kotlin 17 bytecode. The Windows desktop runtime is packaged with the project's GPL Temurin JDK 21 distribution. Use the [Windows shipping skill](../.agents/skills/echo-windows-shipping/SKILL.md) for versioning, packaging, and installer acceptance.
